# Forecast design review and sign-off

Forecast follows Pelagia's feed and site view styling: the shared paper, border, radius, typography, condition colors and existing `site-report-dot` component. Carousel arrows and extra captions, subtitles, descriptions, repeated row dates and update text have been removed. The site name and small local clock lead the view, followed by three calendar tiles, eight three-hour rows and the compact tide chart. Water and air temperature columns use text labels and plain values, without icons. Wind direction uses the same circle, needle and tail geometry as the existing site chart, with neutral colors. Swell height and period remain separate columns with a shared grade. Tide markers show High or Low and the local time, including minutes; they do not label the numeric height.

The eight rows and their headings share one native horizontal scroller with no scrollbar and a pinned time column. Site swiping wraps in both directions; dots and keyboard navigation select sites. Date buttons have their own keyboard controls, and the selected site and date survive navigation back from a site. Table hit targets are 44px high at the default text size. The tide chart has a fixed 132px height and scales to the available width.

Uncached stats shimmer in all 56 metric cells and in the tide area until completion, including HTTP 202 polling and date changes during loading. Slow refreshes reveal the same skeleton after the shared 160ms delay; fast cached transitions do not flash. Forecast navigation has a matching page skeleton. Measured loading and completed states retain identical 45px row heights, 398px table height and 132px tide height. Reduced motion respects the existing application preference.

Forecast calls the same authenticated conditions endpoint and the same shared SQLite forecast cache, coordinate checks, leases, expiry and retry handling as the site page. It does not fetch a second forecast or create a separate upstream cache. The shared weather request includes hourly air temperature, and the normalized response includes three local calendar days. Switching dates is local and makes no additional forecast request. Existing site content and charts are unchanged; links scroll to those charts, with temperature links opening the existing conditions summary.

Visual and interaction review covered 320, 360, 390, 430, 768, 820, 821, 900, 1024 and 1440px widths, 844 x 390 landscape with mobile touch settings, 125% text, both unit systems, long names, a single featured site, multiple sites, empty and unavailable states, retry, delayed responses, refresh, keyboard controls and browser Back. No page overflow, topbar collisions or mobile navigation wrapping was observed. Touch emulation confirmed a circular sequence of all three fixture sites and a 344px stats swipe moving every row together while retaining the current site. Touch validation used Chrome emulation, not a physical device. Screenshots and measurements are saved locally under `output/forecast-review/`.

Validation: all 210 JavaScript tests and 111 focused Python tests pass. Full Python discovery runs 483 tests with one skip; the remaining seven exposure recommendation API errors and one outdated welcome-copy assertion were reproduced against unchanged main (`e9e92f5`) in an isolated baseline copy. Navigation tests were updated to include Forecast between Log dive and Profile. Whitespace checks pass.

Signed off for the Forecast feature's brand consistency, desktop and mobile layout, loading states and interaction behavior, with the existing suite failures documented above.
